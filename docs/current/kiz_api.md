# API КИЗ в объединённой версии WMS

## Аналитическая сводка

`GET /api/kiz-reports/summary` возвращает группировки существующих identity реестра.
Существующий список `GET /api/kiz` не меняется. Новых таблиц и миграций для отчёта нет;
требуется уже существующая схема КИЗ, включая `organization`.

Все параметры необязательны:

| Параметр | По умолчанию | Значение |
|---|---|---|
| `group_by` | `organization,product_id` | Через запятую или повторяющиеся query-параметры. Допустимы organization, product_id, lifecycle_status, location_code, container_id, container_qr_code, origin_type. От 1 до 7 разных измерений. |
| `organization` | без фильтра | Точное, регистрозависимое значение организации. |
| `organization_missing` | без фильтра | true — только NULL organization; false — только заполненные. true несовместим с organization (422). |
| `product_id` | без фильтра | Точный идентификатор товара. |
| `lifecycle_status` | все состояния | registered, active, shipped, error, deactivated. |
| `location_code` | без фильтра | Точный адрес текущего holder: россыпь либо текущий адрес контейнера. Не включает дочерние адреса. |
| `container_id` | без фильтра | Положительный ID текущего контейнера. |
| `container_qr_code` | без фильтра | Точный QR текущего контейнера. При сочетании с container_id оба фильтра должны совпасть. |
| `origin_type` | без фильтра | warehouse_assignment или receipt_import. |
| `origin_reference` | без фильтра | Точное origin_reference, например order_guid поступления. |
| `limit` | 50 | Размер страницы групп, 1–200. |
| `offset` | 0 | Смещение групп, от 0. |

Фильтры объединяются через AND. Неизвестный товар, адрес, организация или контейнер —
200 с нулевыми totals и пустым items, не 404. Пустые строки, неизвестные параметры,
неверные boolean/enum/числа, дубликаты и неизвестные измерения дают 422 с detail.

Примеры:

```text
/api/kiz-reports/summary
/api/kiz-reports/summary?organization_missing=true
/api/kiz-reports/summary?organization=СТАРТ&group_by=product_id,lifecycle_status
/api/kiz-reports/summary?group_by=organization&group_by=product_id&limit=50&offset=0
/api/kiz-reports/summary?lifecycle_status=active&group_by=location_code,container_id
```

Ответ содержит `group_by`, `filters`, `total_groups`, `limit`, `offset`, `totals`,
`items`. Элемент items содержит `group` (только выбранные измерения, включая явные
null) и `counts`. Обе схемы счётчиков одинаковые:

| Счётчик | Смысл |
|---|---|
| `total_count` | Все отфильтрованные записи реестра, включая закрытые и отгруженные. |
| `registered_count` | Зарегистрированные без активации: holder отсутствует, физический остаток не резервируется. |
| `active_count` | Все active identity: идентифицированные единицы организации. |
| `active_loose_count` | Active с прямой локацией и без контейнера. |
| `active_container_count` | Active с контейнером и без прямой локации. |
| `shipped_count` | Отгруженные, не входят в active. |
| `error_count` | Закрытая ошибочная идентификация, не входит в active. |
| `deactivated_count` | Деактивированные, не входят в active. |

Общий количественный остаток inventory и unidentified по организации не вычисляются.
Не зарегистрированные в wms.kiz коды из inbox не учитываются. Сохранённый holder у
error/deactivated не означает подтверждённого физического размещения. История адресов
не реконструируется; location контейнера берётся из его текущего состояния.

Сортировка стабильна по измерениям group_by по возрастанию, NULL сначала. Пагинация
ограничивает только items. totals и total_groups относятся ко всему отфильтрованному
реестру даже при offset за концом списка. Ответ читается в одной read-only транзакции
REPEATABLE READ, без блокировки строк для записи. Отдельные запросы могут видеть
разные состояния при параллельных регистрациях/движениях.

Swagger содержит полные схемы, описания параметров и пример 200. Ошибка БД — 500 без
частичного результата. Подсчёт всех групп требует агрегации отфильтрованного набора:
limit сам по себе не уменьшает стоимость общего подсчёта на больших объёмах.

## Первые 24 символа

Все входные `kiz_code`/`kiz_codes` принимают произвольную длину: запись, поиск,
привязка к СЗ и сравнение используют буквально первые 24 Unicode-символа.
Короткий код используется целиком. Пробелы, GS, переводы строк и регистр не
изменяются. Пустой код, NUL и некорректный Unicode в сохраняемой части запрещены.
Два кода с одинаковыми первыми 24 символами — один КИЗ; дубли в одном запросе
отклоняются после сокращения. Для URL используйте percent-encoding; историю
произвольных кодов безопаснее запрашивать через `GET /api/kiz-history?kiz_code=...`.
Правило действует также в `/api/kiz/assign`, `/activate`, карточке, events,
mark-error/deactivate, `/api/kiz-operations/transfer`, `/ship` и контейнерных fill/extract.
FBS `kiz_bindings[].kiz_code` и импорт `wild_groups[].mark_codes` используют то же правило.

Swagger `/docs` содержит разделы «КИЗ» и «Импорт КИЗ», полные схемы запросов и ответов, примеры и ошибки. Объединённая версия поддерживает назначение, регистрацию из поступления, активацию, чтение, жизненный цикл, перемещение, отгрузку и историю.

## Назначение и остатки

`POST /api/kiz/assign` назначает новый уникальный код одной существующей единице товара:

```json
{
  "kiz_code": "KIZ-TEST-001",
  "product_id": "testwild",
  "location_code": "KIZTEST-SOURCE",
  "author": "operator",
  "metadata": {"comment": "Назначение после сканирования"}
}
```

Нужна минимум одна целая свободная единица доступной россыпи без партии. Товар и точная локация должны существовать. КИЗ получает active, записывается событие assigned. Физическое количество не меняется, движение не создаётся. Код нельзя переиспользовать, даже после закрытия; повтор назначения возвращает 409. Author — записываемое имя оператора, само поле не подтверждает права доступа.

`GET /api/kiz/stock-summary` требует product_id и ровно один из параметров location_code, container_id, container_qr_code. Для россыпи учитывается только точный адрес, для контейнера — его собственный остаток. Дочерние адреса и партии не учитываются. Physical — физическое количество, identified — число active КИЗ, unidentified — разница. При нарушении учёта unidentified может быть отрицательным, integrity_ok=false. Мягкие резервы не вычитаются. Неизвестный товар/адрес даёт 404; неверное сочетание параметров или неизвестный контейнер — 409.

## Реестр, карточка и события

`GET /api/kiz` возвращает items, total, limit и offset. Фильтры: product_id, location_code, lifecycle_status, container_id, container_qr_code. Состояния: registered, active, error, deactivated, shipped. По умолчанию возвращаются все состояния, сортировка по kiz_id по возрастанию. Limit от 1 до 200, по умолчанию 50; offset от 0. Фильтр location_code относится к прямой локации КИЗ, а не адресу контейнера. Для КИЗ внутри контейнера используйте фильтр контейнера.

`GET /api/kiz/{kiz_code}` возвращает карточку. У active КИЗ ровно одно прямое место хранения: location_id для россыпи либо container_id для контейнера. Адрес контейнера находится в container_location_*. У shipped КИЗ прямые места хранения пусты; карточка остаётся доступной.

`GET /api/kiz/{kiz_code}/events` возвращает журнал assigned, marked_as_error, deactivated, shipped с пагинацией limit/offset. Сортировка от ранних событий к поздним. Перемещения и контейнерные операции доступны в полной истории.

Коды регистрозависимы и передаются с URL-кодированием. При назначении запрещены пустые строки, NUL, сегменты пути `.`/`..`, код stock-summary и окончание /events в канонической части.

## Закрытие без физического списания

`POST /api/kiz/{kiz_code}/mark-error` переводит active в error; `POST /api/kiz/{kiz_code}/deactivate` — в deactivated. Обязательны author и непустая reason, metadata необязательна. Поддерживаются КИЗ на россыпи и в контейнере.

Карточка и событие сохраняются атомарно. Физическое количество не меняется; identified уменьшается. Это закрытие идентификации, а не отгрузка товара. Повторное закрытие и возврат в active запрещены; код не освобождается для повторного назначения.

## Перемещение и отгрузка

`POST /api/kiz-operations/transfer` переносит россыпь и выбранные active КИЗ между точными адресами:

```json
{
  "source_system": "manual",
  "external_operation_id": "transfer-testwild-001",
  "author": "operator",
  "items": [{
    "external_line_id": "1",
    "product_id": "testwild",
    "from_location_code": "KIZTEST-SOURCE",
    "to_location_code": "KIZTEST-DESTINATION",
    "quantity": 3,
    "kiz_codes": ["KIZ-TEST-001"]
  }]
}
```

Quantity — полное целое количество, включая КИЗ. В примере перемещаются одна идентифицированная и две неидентифицированные единицы. Пустой kiz_codes допустим, весь расход тогда неидентифицированный. Выбранные КИЗ должны принадлежать товару и находиться на исходном адресе. Товар и адреса должны существовать; source и destination должны различаться. Партии, дочерние адреса и КИЗ в контейнере этим запросом не обрабатываются.

На строку создаётся movement_ref, выбранные КИЗ получают целевой адрес и сохраняют active. Любая ошибка откатывает все строки, движения и изменения КИЗ.

`POST /api/kiz-operations/ship` принимает те же поля, кроме to_location_code. Он создаёт расходное движение, переводит выбранные КИЗ в shipped, очищает location_id/container_id и пишет shipped event. Карточка и история сохраняются. Неидентифицированная часть quantity списывается обычным количественным расходом.

Ключ повтора обеих операций: source_system + тип операции + external_operation_id. Повтор той же команды возвращает сохранённый результат и HTTP 201 без нового движения. Порядок строк и кодов не важен. Изменение external_line_id, товара, адресов, количества или набора КИЗ при том же ключе даёт 409 KIZ_IDEMPOTENCY_CONFLICT с operation_id. Автор сохраняется при первом выполнении; его изменение само по себе не меняет физический смысл команды.

## Полная история и проверка целостности

`GET /api/kiz-history?kiz_code=KIZ-TEST-001` возвращает current_state и полную timeline без пагинации. События берутся из журнала КИЗ, движения — по явным movement_ref. Событие shipped и связанное движение ship объединяются. Для контейнерных операций movement_refs содержит ссылки на физические части операции. Quantity относится ко всему движению, а не к одной единице КИЗ. История доступна и после отгрузки.

`GET /api/system/kiz-integrity` читает нарушения согласованности активных КИЗ и физических остатков. Пустой массив означает отсутствие найденных нарушений. Чтение не исправляет данные.

## Ошибки и ограничения

- 404: КИЗ, товар или адрес не найден. Для неизвестного КИЗ в explicit transfer/ship возвращается 409.
- 409 KIZ_CONFLICT: недостаток остатка, код уже существует, недопустимое состояние или место хранения КИЗ.
- 409 KIZ_IDEMPOTENCY_CONFLICT: ключ физической операции уже использован для другой команды.
- 409 CONCURRENT_WRITE_CONFLICT: конкурентное изменение; физическую операцию следует повторить целиком с тем же ключом.
- 422: формат запроса, обязательные поля или дубликаты; detail содержит список ошибок валидации.
- 500: внутренняя ошибка или нарушенная связь данных.

Импорт receipt КИЗ и активация registered → active входят в объединённый API.
`GET /api/kiz-import/messages` и detail возвращают исходные сообщения; ручной
`POST /api/kiz-import/messages/{message_id}/process` создаёт registered КИЗ без holder
и физического резерва. Включённый consumer выполняет эту регистрацию автоматически.
Товар должен существовать; receipt, его количество, локация и остатки не ограничивают регистрацию.
GUID информационен: другой GUID того же КИЗ не заменяет origin_reference, добавляется связь с сообщением.
receipt_quantity и снимки остатков могут быть null без receipt/локации.
`GET /api/kiz-import/integrity` проверяет holder, origin и связи; отсутствие receipt и расхождения количества информационны, не меняют is_valid.
Старые pending/rejected сообщения повторяются через `/process`; фонового обхода нет.
После миграции 20261023 per-KIZ коррекции товара учитываются при новой доставке
старого кода/товара; это не правило переименования SKU. История `/api/kiz-history`
содержит product_corrected с old/new SKU и причиной из неизменяемого аудита.
Публичный endpoint коррекции не добавляется: это контролируемая maintenance-операция.
Бизнес-ошибка одной группы wild_groups не откатывает валидные группы. Частичный результат:
applied с is_partial=true и rejected_groups (group_index с 0, product_id, error_code, error_message).
Все КИЗ одной группы регистрируются атомарно; повторяющиеся между группами коды отклоняют
все затронутые группы. Общие ошибки supply/JSON и отказ всех групп дают rejected.
Системная ошибка откатывает весь message. Replay applied возвращает сохранённые отказы;
для исправления источник присылает новое сообщение с корректными данными.
`POST /api/kiz/activate` подтверждает сканирование в loose location без движения товара.
Карточки, список, журнал и история поддерживают registered, receipt_import и события
registered/activated; карточка также возвращает nullable organization.

FBS task-level flow принимает optional kiz_bindings. Registered КИЗ списывается из
FBS zone, active loose КИЗ — из фактического holder. КИЗ внутри контейнера не входит в
FBS Stage 1; используются управляемые контейнерные операции. Обычный количественный
расход защищает active identified часть: при physical=3 и identified=2 без выбора КИЗ
можно расходовать только одну единицу.
